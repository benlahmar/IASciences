Peut-on faire confiance à une prédiction d'IA ?

Une grande précision sur les données disponibles ne démontre pas qu'un système soit fiable dans un autre laboratoire, pour une autre population ou dans de nouvelles conditions de mesure. La validité dépend autant du protocole scientifique que de l'algorithme.

Objectifs : repérer les fuites de données et les biais, choisir une validation pertinente, distinguer explication et causalité, quantifier l'incertitude et documenter les usages responsables de l'IA.

1. Performance apparente et généralisation

Une performance obtenue sur les données d'entraînement mesure d'abord l'ajustement au passé. Pour estimer la généralisation, on sépare entraînement, validation et test indépendant. L'ensemble de test ne doit pas servir à sélectionner les modèles.

Erreur de généralisation ≈ moyenne sur des observations nouvelles et indépendantes

En sciences, « indépendant » doit être défini : réplicats d'un même échantillon, mesures d'un même patient, acquisitions d'un même capteur ou observations voisines dans l'espace ne sont pas nécessairement indépendants.

2. Fuite de données : un modèle peut tricher sans le savoir

Une fuite apparaît lorsque des informations qui ne seraient pas disponibles lors de l'utilisation réelle contaminent l'entraînement ou l'évaluation. Exemples : normaliser les données avant de définir les ensembles ; mélanger des mesures répétées d'un même échantillon entre train et test ; utiliser un résultat de laboratoire ultérieur comme variable prédictive.

Bonne pratique : faire la séparation en premier, puis ajuster tout prétraitement uniquement sur les données d'entraînement, par exemple avec un Pipeline Scikit-learn. Utiliser une séparation par groupe ou par date lorsqu'elle reflète l'usage réel.

3. Biais et décalage de distribution

La collecte peut surreprésenter certaines zones géographiques, conditions expérimentales, lignées cellulaires ou appareils. Le modèle apprend alors des associations propres à cette collecte. Lors du déploiement, les distributions peuvent changer : capteur différent, saison différente, population différente ou protocole révisé.

5. Explicabilité ≠ causalité

Une importance des variables, une explication locale de type SHAP ou un graphique de dépendance partielle décrivent le comportement d'un modèle dans un cadre donné. Ils ne prouvent pas qu'une variable cause le phénomène. Il faut examiner les interactions, les variables corrélées et les hypothèses de l'outil d'explication.

Corrélation(X,Y) ≠ preuve de causalité X → Y

Exemple : si la provenance d'une plaque de laboratoire prédit fortement une classe biologique, cela peut révéler un artefact expérimental plutôt qu'un mécanisme biologique.

6. Incertitude et robustesse

Différencier le bruit des observations (incertitude aléatoire) et les limites du modèle et du jeu de données (incertitude épistémique). Une moyenne prédite sans intervalle ni domaine de validité peut donner une illusion de certitude. Vérifier la calibration, les sous-groupes et les observations hors distribution.

7. Intégrité scientifique, transparence et éthique

Déclarer l'origine des données, les transformations, les versions des logiciels, les partitions d'évaluation et l'usage des assistants génératifs. Éviter de transmettre des données sensibles à un service externe sans autorisation. Vérifier les références, figures et interprétations. Conserver une validation humaine des conclusions scientifiques.

Checklist d'une étude reproductible : question et population définies ; données traçables ; séparation adaptée ; baseline ; métriques appropriées ; intervalles ou incertitudes ; analyse des erreurs ; code et environnement décrits ; limites et usages de l'IA déclarés.

Auditer une expérience d'apprentissage

Exercice 1 — Une précision de 98 % (12 min)

On dispose de 600 images de 30 lames biologiques. Les images sont séparées aléatoirement : 98 % de précision test. Peut-on conclure à une généralisation à de nouvelles lames ? Proposer un protocole.

Voir le corrigé

Non : plusieurs images d'une même lame sont corrélées. Les lames peuvent être présentes dans les deux ensembles, générant une fuite par identité de l'échantillon. Séparer par identifiant de lame avec GroupShuffleSplit ou GroupKFold ; si possible, tester sur un lot ou un laboratoire indépendant.

Exercice 2 — Prétraitement et fuite (12 min)

Une équipe calcule la moyenne et l'écart-type sur tout le dataset, standardise, puis effectue une validation croisée. Où se trouve le problème ?

Voir le corrigé

Les statistiques des observations de validation ont influencé le prétraitement. Créer le découpage en amont et placer StandardScaler dans un Pipeline entraîné dans chaque pli. Attention aussi aux imputations et sélections de variables effectuées hors validation croisée.

Exercice 3 — Quelle métrique ? (12 min)

Sur 1000 échantillons, 20 sont positifs. Un classifieur prédit toujours « négatif ». Calculer l'accuracy et le rappel de la classe positive.

Voir le corrigé

Accuracy = 980/1000 = 98 %. Rappel positif = 0/20 = 0 %. L'accuracy masque complètement l'échec sur la classe recherchée. Examiner rappel, précision, matrice de confusion et coût scientifique des erreurs.

Exercice 4 — Explication ou preuve ? (12 min)

Un modèle de concentration estime que « numéro d'appareil » est la variable la plus importante. Peut-on conclure que l'appareil cause directement les variations chimiques ?

Voir le corrigé

Non. L'appareil peut être corrélé à un lot, une date ou un protocole. L'importance décrit une association utilisée par le modèle. Comparer des appareils sur les mêmes échantillons et contrôler les facteurs de confusion avant une interprétation causale.

Exercice 5 — Audit de publication (12 min)

Un article présente F1=0,93, sans indiquer les partitions, la provenance des données, les intervalles de confiance ni le code. Proposez cinq questions de relecture.

Voir le corrigé

(1) Comment sont construits les groupes train/test ? (2) La métrique concerne-t-elle un test réellement indépendant ? (3) Existe-t-il une baseline ? (4) Quels sont les résultats par sous-groupe et l'incertitude ? (5) Le code, les versions et les transformations sont-ils reproductibles ? Il faut également questionner l'origine et les autorisations des données.

Notebook : la normalisation dans une validation croisée

Comparer un prétraitement effectué sur la totalité du jeu de données avec un Pipeline conforme. L'exemple ci-dessous montre la bonne pratique de validation ; il ne garantit pas que les scores soient très différents sur chaque jeu de données.

import numpy as np
from sklearn.datasets import make_classification
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import StratifiedKFold, cross_val_score

X, y = make_classification(
    n_samples=320, n_features=12, n_informative=5,
    weights=[0.8, 0.2], random_state=42
)
model = make_pipeline(StandardScaler(), LogisticRegression(max_iter=1000))
cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=42)
for metric in ['accuracy', 'balanced_accuracy', 'f1']:
    scores = cross_val_score(model, X, y, cv=cv, scoring=metric)
    print(metric, round(scores.mean(), 3), '+/-', round(scores.std(), 3))

Questions : pourquoi une précision globale élevée est-elle insuffisante avec des classes déséquilibrées ? Pourquoi le Pipeline doit-il être recalibré dans chaque pli ? Comment modifier le protocole si plusieurs observations viennent d'un même échantillon ?
